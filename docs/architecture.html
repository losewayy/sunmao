From prompt to tool call,
and the seams in between

A Rust agent harness whose organizing principle is joinery: the kernel is a bus of replaceable ctx.* services, every extension crosses a process boundary, and the single source of truth is an append-only event log. This page traces one turn end-to-end, then maps the subsystem seams that make it swappable.

01

The pipeline: prompt → tool call

One run_turn inside AgentLoop. Everything durable becomes a SessionEvent line; everything live becomes an Observer callback. The frontend (REPL / TUI / ACP client) only ever sees those two streams.

01

Prompt in run_turn(input)

Caller hands over a raw user string and an Observer. Cancellation is re-armed (ctx.cancelled.store(false)) — a session/cancel from a frontend sets it back to true mid-flight.

02

UserPromptSubmit hooks ctx.hooks.fire(UserPromptSubmit)

External commands run before the prompt is committed. A hook may veto (block_reason → turn aborts with TurnOutcome::Other) or inject (extra_context → appended as [hook context] user messages).

block_reason extra_context
03

Commit the user turn sessions.append(Message)

Exactly one user/message event is written to {session}.jsonl, followed by any injected context. The log is the truth; the message list is a fold over it, so replay and fork cost nothing extra.

SessionEvent::Message
loop — up to 64 iterations
04

Budget & compaction est_tokens() > 180_000

Bytes/4 estimate over the folded transcript. Crossing the ceiling triggers compact(): the model summarizes, and a Compacted boundary event is appended — the fold then resets to a fresh system message.

SessionEvent::Compacted
05

Build the request messages() + tools.declarations()

Fold the log into protocol messages; ask the registry for tool schemas. The request is a plain ChatRequest — no hidden state rides along.

06

Stream the model ctx.llm.stream(req)

Hand-written SSE parsing. Deltas arrive as Content, Reasoning, ToolCalls (fragmented!) and Finish. Content and reasoning are forwarded live to the observer as they land — token-by-token, no buffering.

LiveEvent::Content LiveEvent::Reasoning LiveEvent::Finish
07

Reassemble tool calls ToolCallAssembler.finish()

OpenAI-compatible endpoints ship tool_calls as index-keyed fragments across many chunks. The assembler stitches them back into complete calls — including tolerating dirty payloads (null fragments, unknown finish reasons).

08

Commit the assistant message sessions.append(Message)

Content (if any) plus the assembled tool_calls land as one assistant/message. From here the turn either ends or descends into tools.

SessionEvent::Message
09

No tool calls? Turn ends finish_reason → TurnOutcome

stop/end_turn/absent → Completed; length → LengthLimited; anything else → Other(reason). The loop breaks and the Stop hook fires.

10

Record the dispatch sessions.append(ToolCall)

Every call is journaled before execution — so a crash mid-tool still leaves a truthful record of intent.

SessionEvent::ToolCall ×N
11

PreToolUse gate ctx.hooks.fire(PreToolUse, name, input)

Matcher-filtered hooks see the tool name and parsed arguments. A block_reason short-circuits execution: the call returns a synthetic failed result the model can read.

veto → synthetic ToolResult{ok:false}
12

Execute the tool ctx.tools.call(name, args, ctx)

Arguments are parsed to JSON, then dispatched by name. Bash routes through the risk classifier and the approval gate before anything spawns; failures are returned as legible output, not panics — models recover better from readable errors.

unknown tool / bad args → ok:false RISKY_PATTERNS → ctx.approval.approve()
13

PostToolUse hooks ctx.hooks.fire(PostToolUse, …, result)

Hooks observe the result and may push extra_context back into the transcript as user messages — the injection path that lets a hook steer the next iteration.

extra_context → [hook context]
14

Commit the result, iterate sessions.append(ToolResult)

The result is journaled with its call_id, then control returns to step 04. Next iteration folds a longer log and re-streams the model.

SessionEvent::ToolResult ↻ back to step 04
15

Stop & hand back hooks.fire(Stop) → LiveEvent::TurnEnd

The terminal hook fires, the observer receives the TurnOutcome, and run_turn returns. Frontends differ only in who implements Observer.

03

Where the seams are

Three distinct kinds of cut, and they are not interchangeable. Confusing them is how a seam-first kernel turns into abstraction tax.

In-process trait seams — Context

The kernel context is a struct of services. Exactly two are trait objects today: llm: Arc<dyn ProviderAdapter> and approval: Arc<dyn Approver> — each has (or imminently has) a second implementation. The rest (sessions, tools, audit, hooks) are concrete types, promoted to traits only when a real second impl appears.

file: core/src/context.rs · 81 LOC · swap by constructing a new Context

Process boundaries — the extension surface

Crashes are isolated, languages don't matter, and every interaction is interceptable: hooks (Claude contract, JSON on stdin), MCP servers (stdio), and the ACP bridge outward. The extension never links into the kernel; it talks to it.

failure model: a dead extension degrades a capability, never the agent

Data seams — the event log

Every durable fact funnels through one append-only writer. The read side is a pure fold. That single choke point is what makes transcript files, replay, fork, and dataflow --emit "what data went where" reports free rather than bespoke features.

file: core/src/session.rs · append() is the only mutation path

Tool-execution seams — the three-class ladder

Not a seam between modules but a deliberate gradient of opacity: native (in-process Rust, structured tool_input, zero shell) → managed (spawned binary, no shell, controlled env) → shell (Bash: an opaque command string, the primary audit target). Everything that can be native, is.

the shell escape hatch is a deliberate exception, not the foundation

Loop seam — the loop is a plugin

AgentLoop holds no kernel privilege. It is one driver over the same Context; a minimal loop, a code-mode loop, or a strict-audit loop are all presets — plugin stacking (base → +tui → +acp → +strict-audit), not --flag branching.

file: core/src/agent.rs · 332 LOC · "swap the loop, swap the product"

Interception seam — the pre/exec/post spine

One tool call is a three-slot pipeline: pre (hooks + approval) → exec (registry dispatch) → post (hooks + context injection). Both ends are public to ctx.audit and ctx.hooks, so policy and telemetry attach without the tool layer knowing they exist.

file: core/src/agent.rs steps 11–13 · the wiring is in the loop, not the tools
The discipline that keeps this honest: a seam is only cut when a second implementation already exists or is imminent — no empty interfaces "for the future." The core has a line budget, every abstraction must save more code than it costs, and any state has exactly one owner (session facts live only in the log; tool registrations live in one table). Deleting is the cheapest maintenance. When the kernel can't justify the seam, it ships the concrete thing and waits.
